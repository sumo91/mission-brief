# Mission Brief 第二次极简重构计划

## 目标

把 Mission Brief 运行时从评估补丁逐渐沉积形成的规则集合，重构成一份普通 Agent 能够一遍读懂并稳定执行的工作说明，同时保留最初目标：

> 将已经采用的委托交给缺少原始规划上下文的执行 Agent，使其能够恢复结果、证明义务、硬边界和适用权威，找到必要的已知信息，并依据最新现场独立选择路线。

最终成败由新鲜执行 Agent 的实际交接和下游结果决定，而不是由字数、规则数量、流程完整度或评估记录体量决定。

## 实施原则

1. **结果优先。** 流程和评估只用于降低错误风险，不作为交付物本身。能够以更小成本回答决定性问题时，不追加仪式。
2. **能力默认。** 假设当前 Agent 已能处理普通规划、文件检查和语言表达，只保留会改变其决定的非显然信息。
3. **正向引导。** 先说明应形成的结果；只有不可由正向目标覆盖的真实硬边界才使用禁止语句。
4. **一次定义。** 一个含义只在一个权威位置定义；其他位置使用稳定名称，不重复换词枚举。
5. **按分支披露。** 所有 Mission 都需要的信息留在主文件，只有集成拓扑或复杂来源需要的信息分别进入条件 reference。
6. **失败不自动产规则。** 单次评估失败先区分领域缺陷、表达缺陷、harness 缺陷和随机波动；只有前两类且不能从现有原则自然推出时才修改运行时。
7. **适度验证。** 迭代期使用小型 smoke set；候选冻结后才运行一次完整回归和盲交接。测试不因已有 runner 就自动执行。
8. **实际效度。** 发布前比较普通交接、当前版本和极简候选对后续执行的影响，而不只比较 Brief 文本是否符合内部评分合同。

## 范围

### 保留

- Mission Brief 是结果合同，不是实施计划。
- 一个 Mission 对应一个可独立裁决的结果。
- 只固化已采用决定和适用权威。
- Authority Source 与 Reference Source 保持不同权威状态。
- 每项重要信息获得一个持久去向。
- 证据挑战实际结果，不把代理指标当成完整证明。
- 执行 Agent 保留路线自由。
- Mission 0 负责不可约的整体结果和接缝。
- 新鲜 Agent 可以恢复合同、来源和可行执行空间。

### 改善

- 减少不必要追问、阻塞和文件写入拒绝。
- 消除多套相近但不同的合同维度清单。
- 让主路径使用的术语都在主路径得到定义。
- 用少量原则和理由替换否定枚举与案例补丁。
- 让完成条件可以被 Agent 真实检查。
- 降低普通路径和条件路径的上下文负担。
- 验证 GPT 与 Fable 对同一运行时的理解差异。

### 不做

- 不重新设计 Mission Review。
- 不改变默认 Mission 存放目录和 `brief.md` 文件名。
- 不改变显式调用策略。
- 不引入新的生命周期、状态机、审批流程或目录层级。
- 不在本轮全面迁移 Mission 0 的既有名称和文件路径。
- 不继续扩充当前行为场景以覆盖每一种措辞。
- 不把 README、CONTEXT 或评估合同变成运行时依赖。

## 信息模型

### Contract Core

所有 Brief 都表达同一组合同核心：

1. `Outcome`：最终发生的用户或系统变化。
2. `Success`：区分成功和相似失败的事实。
3. `Evidence Required`：怎样挑战这些事实。
4. `Boundaries`：会改变合法执行的硬限制。

这是唯一的规范性维度清单。

### Complete handoff

完整交接在 Contract Core 之外按实际情况补足：

- 结果所属目标或保存边界；
- 适用权威；
- 必要且持久的上下文；
- 已采用的父子拓扑；
- 来源状态和可解析链接。

运行时只命名反复使用的 `Contract Core`。其余交接信息在盲交接终检中就地表达，不再为只使用一次的层次创造术语。

### 主路径术语

- **Material information**：丢失后可能改变合同、显著提高执行风险，或迫使执行者重复昂贵调查的信息。
- **Authority Source**：其适用内容能够约束当前 Mission 的来源。
- **Reference Source**：保存有用事实、理由或候选路线，但不会因保留或链接自动获得约束力的来源。
- **Route freedom**：合同固定终点、证明和硬边界，执行者依据最新现场选择路线。
- **Information home**：一项 material information 的唯一持久去向；可以是 Brief、带权威状态的持久来源、后果重大的未决决定或有理由的省略。

用自然词 `home` 取代 `honest disposition` 作为主要执行概念。

## `SKILL.md` 设计

### 产品边界

开头只说明：

- Mission Brief 冻结已经采用的结果合同。
- 它不评审候选方案、不形成实施计划，也不执行 Mission。
- 一个请求同时需要其他产品时分别交付，不把两种产品混写。

删除 implementation-shaped nouns 的长枚举。

### 四项原则

1. **Outcome over route。** 执行者拥有更新鲜的环境信息，因此 Brief 规定终点、证明和硬边界，路线默认留给执行阶段。
2. **Source status。** 链接保存访问能力，不转移权威；只有采用的决定和适用 Authority Source 约束合同。
3. **One home。** 每项 material information 只有一个持久去向，避免丢失和重复约束。
4. **Falsifying proof。** 证据必须能让承诺失败；测试、截图和结构检查只证明它们实际覆盖的行为。

### 四步工作流

#### 1. Recover the commission

当采用的事实支持一个合理、单一、可独立裁决的结果时直接综合，不要求用户重新填写模板。只有不同答案会形成不同结果时才询问。

完成条件：能够说出一个具有独立价值的可观察结果；如果涉及集成结果，相关拓扑已经采用。

#### 2. Settle consequential decisions

只在未决答案会改变 Contract Core、Authority、已采用拓扑，或造成 material information 永久丢失时停止。安全可发现的根因、文件位置、工具和架构留给执行阶段。

完成条件：写入不会虚构产品决定、绕过权威冲突或丢失不可恢复的重要信息。

#### 3. Write the current contract

使用四个核心标题，按需增加 `Intent`、`Non-goals`、`Context`、`Execution Authority`、`Parent Mission` 或 `Result Boundaries`。`Context` 对所有路径开放；source-fidelity 只处理复杂来源。

从当前采用的合同重新起草。历史路线留在原来源中；只有仍有效的兼容义务、明确禁止或权威边界进入 Brief。

完成条件：Contract Core 完整，每项 material information 都有一个 home，Brief 没有把可选路线变成命令。

#### 4. Save and hand off

依次采用用户指定路径、仓库既有约定、`docs/missions/<outcome-slug>/brief.md`。保留现有 Mission 0 存储规则。

终检只有四问：

1. 新 Agent 能否复述 Contract Core？
2. 它能否找到必要上下文并识别来源权威？
3. 它能否说明什么证据支持 `PASSED`、`FAILED` 或 `INCONCLUSIVE`？
4. 它能否选择不依赖作者隐藏上下文的可行路线？

全部为“是”才完成。

### 示例

在主文件保留一份 15–20 行的完整普通 Brief，使用 Safari 回车提交登录表单的例子，展示结果、相似失败、兼容边界和真实验证，不包含实施路线。

另保留一个极短的停止示例：来源存在两个未采用且会改变授权模型的方案时，指出被影响的合同部分并询问采用哪一个；决定前不写 Brief。

完整正例取代空模板和一部分规则解释，不增加 examples 文件。

## 条件 references

### `source-fidelity.md`

只保留：

- 混合来源如何区分决定、事实、候选路线和过时材料；
- 临时附件如何获得持久去向；
- 已完成调查如何保留事实和因果关系；
- 何时需要独立 `context.md`。

删除主文件已经定义的 material、route freedom、information home 和历史路线扫描规则。

完成条件：每项 material information 都可以从持久位置恢复，且其权威状态准确。

### `mission-zero.md`

使用一次自然别名 `Integration Mission (Mission 0)`，保留现有名称以兼容既有文档。只保留：

- 何时提出集成结果；
- 用户采用整体结果、结果边界和跨结果不变量；
- parent 拥有接缝，child 拥有局部合同；
- 父子链接、存放位置和后续更新规则。

删除关于“什么不是 topology trigger”的多项否定和与主文件重复的权威、证明及来源规则。

完成条件：parent 可以独立判断整体成败，child 可以恢复适用 parent 不变量，目录只表达已委托的结果。

### 阶段 1：建立临时删除清单

逐段把旧运行时标为保留、改写、移入分支或删除。清单只服务本次重写，不提交为新的长期规范。

完成条件：每段旧规则都有去向，没有因“留着更安全”而默认保留。

### 阶段 2：一次性重写主文件

按照产品边界、四项原则、四步流程、完整示例和四问终检重新起草，不在旧文上逐句压缩。先保证自然清楚，再检查体量。

### 阶段 3：重写条件 references

公共定义回到主文件；reference 只保留分支独有决定。检查每个 pointer 只表达真实触发条件。

### 阶段 4：快速行为循环

迭代期只跑约八个高价值案例：普通回归、确定来源、多结果、权威冲突、混合来源、临时来源、Mission 0 和历史路线残留。

失败先归因。现有原则可以推出正确行为时，优先改善表达或评估，不追加规则。

### 阶段 5：冻结候选并完整回归

候选冻结后运行结构验证、30 个行为案例、3 个 Loader 案例和两个盲交接。只运行一次完整主回归；harness 修复单独提交，并同时验证稳定基线和候选。

### 阶段 6：真实下游 A/B

作者层比较普通交接、当前 Skill 和极简候选，覆盖普通 Mission、详细方案、混合权威、临时来源、集成 Mission 和应当停止的决定。

从可实施案例中选择三个，让新鲜 Agent 真正执行，再由独立 Mission Review 检查实际产物。衡量实际结果、信息丢失、路线锚定、不必要追问、交互轮数、token 和延迟。

先在 GPT-5.6 上进行；无实质回归后，再用 Fable 5.1 运行相同作者任务。只对争议案例增加重复，不机械扩大样本。

### 阶段 7：独立会话审查与发布

全新会话只接收最初目标、冻结候选、必要原始任务、实际 A/B 结果和稳定基线，不接收作者预期、历史失败诊断或修改理由。

独立审查重点回答：新 Skill 是否以更少注意力成本，更可靠地让新鲜执行 Agent 恢复合同、信息和路线自由，并改善或至少不损害实际结果。

审查通过后更新 README 和 CONTEXT，必要时做 Mission Review 术语兼容，同步本机 Skill，验证仓库与安装内容一致，记录发布结论并打包。

## 发布条件

### 结构

- 主路径需要的术语都在主路径定义。
- Contract Core 只有一份定义，其他交接要求只在终检中出现一次。
- 每项运行时行为只有一个权威位置。
- 没有单案例专用句子和不可执行终检。
- 普通路径不加载条件 reference。

### 行为

- 现有完整行为套件和盲交接无实质回归。
- 不增加不必要阻塞。
- 不降低来源保真、权威识别、Mission 0 连续性和路线自由。
- 临时来源不会成为交接后的唯一信息载体。

### 实际效果

- 下游执行结果不低于当前版本。
- 复杂来源交接明显优于普通摘要。
- 没有新增路线锚定。
- 澄清轮数和总体 token 至少一项明确改善，另一项不显著恶化。
- 如果声明支持 Fable，则 Fable 上没有模型特有的发布阻断问题。

字数下降但实际结果下降时不发布。流程证据不完整但决定性结果已经清楚时，补最小必要证据，不为形式完整无限延长实施。
