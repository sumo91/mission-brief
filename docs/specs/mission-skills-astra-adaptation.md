# Mission Skills 面向 GPT-6 Astra 的设计与实施方案

日期：2026-09-05

状态：用户已批准实施，三个 Skill 的适配、完整当前案例覆盖、新鲜交接、独立 Closure 及本地安装均已完成。详见[实施记录](../reviews/2026-09-05-astra-adaptation.md)。

分析基线：`32c1d2a7e91c494e89e1d1b4f5e9a68c52c177f4`。

本文把三个 Skill 的模型适配建议转成可实施方案。它是维护者设计文档，不是 Mission Brief，不进入运行时安装目录。涉及既有产品规则的调整，在实施时同步更新当前规格和评估；历史决定、原始回归材料与旧运行证据保留原样。

实施收尾遵守用户补充约束：避免审查驱动的 Skill 膨胀。仅因实质行为缺陷修改运行时；措辞偏好与评分误判在评估层处理。保留小型运行时及按需读取，不把测试案例、评审过程或模型调参说明装入 Skill。

## 1. 目标与设计依据

让 Agent 在保留结果契约、来源保真和真实验收的条件下，减少重复确认、交接停顿和无新增价值的检查。模型应能完成已授权的原请求，准确吸收用户修正，并让后续执行者恢复仍然有效的决定与证据。

OpenAI 的 [Astra 提示词指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra#prompting-best-practices)指出：Astra 更容易澄清，对 Skill 指令更敏感，也可能在小任务上做过多测试；需要子代理时应明确委派条件。这支持检查现有门槛，但不证明删除某条规则必然改善结果。改动效果以对照运行验证。

本轮保留：

- `mission-align` 对齐、`mission-brief` 写合同、`mission-review` 验收的三项职责。
- 一个 Mission 对应一个可独立判断的结果；Mission 0 只拥有真实的集成结果和接缝。
- `Outcome`、`Success`、`Evidence Required`、`Boundaries` 四项合同核心。
- 来源的实际权威状态、重要信息的持久去向和执行路线自由。
- 对重大未决选择、实际权威冲突和明确的人类决定保留必要确认。
- `PASSED`、`FAILED`、`INCONCLUSIVE` 的实质判断。
- Align 允许自动发现，Brief 和 Review 保持显式调用；运行时分别保持两、四、两个文件。

本轮采用一个跨模型通用版本，以 Astra 为主要验证对象。不增加第四个管理 Skill、模型专属分支、生命周期服务、通用审批框架或强制配套文档。推理档位等模型配置留在评估与运行环境中。

## 2. Mission Align：明确采纳范围，恢复原请求

### 2.1 确认规则

保留对最终理解的一次明确采纳，按意思判断确认，不要求固定口令。用户看到完整摘要后的明确修正，可以同时完成对修正后摘要的采纳。

| 当前输入 | 目标行为 |
| --- | --- |
| Agent 刚提出完整摘要，用户尚未回应 | 请求确认或修正，不宣称已对齐。 |
| 用户明确接受摘要 | 完成对齐；不再请求同一确认。 |
| 用户说“退款也包含，但只包含终态失败，其他都对” | 若修正含义完整且不引出新冲突，采纳修正并保留其余内容，简述变化后交接。 |
| 用户只说“差不多”或保持沉默 | 不视为确认；只问尚未确定的部分。 |
| 用户说“要不把退款也加上？” | 视为候选讨论，说明后果，不立即改写已采用决定。 |
| 修改影响了尚未决定的权限、兼容性或成功含义 | 保留未受影响的决定，只询问新出现的重大选择。 |
| 用户明确委派某项选择 | 在该范围内决定；不扩展成全局授权。用户明确免除范围内的再次确认时遵从该指示，仍保留适用的外部授权条件。 |

删除“任何重要修正都必须重新确认全部摘要”的无条件要求。修改后的完成标准是：当前结果及其重大边界已经被明确采纳，或相应选择已被明确委派；不存在被模型私自决定的重大分歧。

### 2.2 按入口交接

交接依赖原请求，不由 Skill 结束位置决定整项任务结束。无需增加持久状态字段，使用当前会话中可恢复的原请求即可。

| 入口与已授权范围 | 对齐完成后的行为 |
| --- | --- |
| 用户只要求 `$mission-align` | 交付对齐结果；如果下一步是 Brief，提供可用调用，不开始实施。 |
| 用户已调用 `$mission-brief`，它为消除复杂分歧进入 Align | 返回已发起的 Brief 工作，生成并保存已授权的 Brief；不要求用户再输入一次同样的调用。 |
| 普通实施请求已经清楚 | 不自动插入对齐或 Brief 仪式。 |
| 用户要求先研究或设计，再决定是否立项 | 对齐下一产品；由原请求负责继续已授权的研究或设计，不把它替换成 Brief。 |
| 用户已明确取消或替换原请求 | 遵从新范围，不恢复已取消工作。 |

这里的“返回 Brief”是完成已经显式发起的委托，不是从 Align 自动创建一个新的手动 Skill 调用，也不表示创建新会话。[Codex 调用策略](https://learn.chatgpt.com/docs/build-skills)继续由 `agents/openai.yaml` 控制。

### 2.3 等待决定时的工作

允许继续已经授权、且不依赖待答选择的材料阅读、事实核实和来源整理。只做有助于当前对齐的合理调查；把可安全留给执行阶段的实现事实继续留在那里。

若宿主有异步提问能力，可用于非阻塞问题；没有则使用普通对话。工具可用性不成为对齐的前置条件。需要真实答复的分支始终等待，不以等待超时推定同意，也不在等待期间写入未定合同或实施争议方案。

## 3. Mission Brief：保存有效授权与变化后的合同

### 3.1 恢复已有授权

使用现有可选 `Execution Authority`，只记录会影响后续行动的具体授权信息：用户已委派的选择、已授权的动作，以及仍需要特定主体决定的事项。

例如，用户已允许决定实现路线并修改本地代码，但上线需要发布负责人批准，Brief 应使两者都可恢复。写 Brief 本身不会自动启动实施，也不会创造用户尚未授予的权限。普通小委托无需填通用授权模板。

### 3.2 同一委托的明确修正

采用以下局部更新规则：

1. 判断新输入是明确决定、事实发现，还是讨论中的方案。
2. 明确的新决定只替换受影响部分；未受影响的结果、边界与授权继续有效。
3. 必要时同步受影响的 Success、Evidence Required 和父子链接，避免正文与证据义务不一致。
4. 新事实若揭示真正的合同或权威冲突，指出冲突；不把事实发现自动解释成用户改变目标。
5. 同一委托更新原 `brief.md`。不同的独立结果仍按现有规则另立委托。

当前 Brief 保持干净的现行合同。需要追溯时利用原消息、现有来源和 Git 历史；没有追溯价值时不额外生成变更日志、版本目录或新表单。

### 3.3 信息保存属于已有授权内的执行判断

当用户已授权仓库内保存，且存在合适文档边界时，Agent 为重要信息选择持久去向。优先复用现有来源，其次放进 Brief 的必要上下文，只有确有内容时创建配套记录。

保留已采用的 child 局部合同，不等于立项 child 或把它们复制进父级。保存时保留原权威状态和“尚未单独立项”的事实。

仅在保存会改变保密范围、访问权限、合同效力，或确无授权可用的持久位置时提出相关问题。避免把“放在哪里”默认提升为必须由用户决定的事项。

### 3.4 保留按需引用与路线自由

继续由主 Skill 定义通用原则；`source-fidelity.md` 只承担混合来源、临时材料和重要调查保真的特殊规则。新规则就地修改，不在三个 Skill 和两个引用中重复铺开。

Mission 0 保留现有判断与存储方式。若集成结果和边界已经明确被采用，直接使用已有决定；只有新的集成选择才需要提出建议。使用子代理本身不构成创建 Child Mission 的理由。

## 4. Mission Review：让裁决与证据适用范围一致

### 4.1 标识实际受审结果

裁决对应受审合同和产物的可识别状态。按环境使用提交、相关文件摘要、部署标识或明确的检查时间与可见状态。工作区有未提交修改时，单独记录 HEAD 不足以标识受审内容。

检查期间如果结果变化，先判断哪些承诺受到影响，再补查对应行为。只检查过旧结果时，限定旧版本结论；无法确定新结果时，不将旧证据直接迁移成当前 `PASSED`。

这是结果身份记录，不是新增版本管理系统，也不要求为所有普通阅读任务计算整个仓库的摘要。

### 4.2 复用与补查

| 现有证据 | 如何处理 |
| --- | --- |
| 来源可追溯、覆盖当前承诺、产物和关键环境仍适用 | 可以复用；独立复现有疑点或决定性部分，避免机械重跑整套检查。 |
| 只有实现者“已完成”的描述 | 作为线索，检查实际结果。 |
| 版本或环境已经变化 | 识别影响范围，补查受影响行为。 |
| 合同明确要求独立执行或特定的人类决定 | 仍完成该义务，不能用复用免除。 |
| 决定性事实经过可行检查仍不可取得 | 限定已知事实，裁决为 `INCONCLUSIVE`。 |

保留直接尝试真实阅读、追证或使用任务的要求。通过裁决需要所有重大承诺获得相称支持；一个决定性的失败可以支持 `FAILED`。已有足够证据后，只因新变化、新反证或未解疑点继续检查，不为了找足数量追加问题。

### 4.3 独立性与职责

优先使用已有的新鲜审查上下文；当主审参与过实现，或读者任务明显受先验解释影响时，使用不带实现诊断的独立尝试。普通检查不要求子代理。

独立尝试只接收原始合同、最终产物、必要环境和任务，不接收预期裁决、疑似缺陷、先前批评或作者解释。换一个 Agent 名字、同时继承完整实现历史，不构成盲测。

主审核对决定性观察，保留最终判断责任；子代理观察不能替代合同指定的人类批准。没有可用独立上下文时如实标注，是否影响裁决取决于独立性是不是实质证明义务。

用户同时要求审查与修复时，先记录受审版本的裁决，再进入另外已授权的修复阶段。修复后的结果另行验证，不把改后通过追记成改前通过。

## 6. 评估设计

### 6.1 对照与身份

主要对照：同一个 Astra 执行配置下，基线运行时与候选运行时接收相同原始输入，由相同的修订后语义标准评分。改变的产品规则单独标记，避免把基线遵守旧规则说成模型错误。

固定并记录：实际解析到的执行模型、推理档位、裁判模型、Codex/harness 版本、工具与权限、完整运行时摘要、案例集合、评分规则和原始轨迹。接缝案例同时绑定 Align 与 Brief 的实际文件身份，不能只记录根 Skill。

默认以 Astra `medium` 作为本轮主实验配置，先核实 harness 确实支持并生效；它是实验起点，不是所有任务的最佳档位结论。遇到复杂任务异常时，可用一个更高档位诊断，但不得以该次通过替换原条件下的失败。裁判与执行者上下文隔离，不能看到候选标签与预期优劣。

当前 runner 支持显式 `--model`，但本仓库入口没有显式推理档位参数。先检查底层配置的实际值；缺少可控入口时，只增加本实验需要的参数透传和记录，不猜测默认值或假装已经固定。

旧版 Sol 证据保留为历史参考。只有要对外声称仍兼容前代模型时，才在该模型上运行针对性兼容回归。普通提示词对照只在需要判断 Skill 是否提供额外价值时使用，并给它相同产品任务，不能比较不同请求。

### 6.2 最小行为矩阵

以下是案例组，不要求逐行新建文件；优先修改或扩展现有案例。

| 编号 | 场景 | 可观察预期 |
| --- | --- | --- |
| A1 | 首次摘要、明确确认、含糊回应 | 首次采纳真实发生；明确接受后不重复问；含糊回应不算通过。 |
| A2 | 明确局部修正与候选式提问 | 前者更新受影响内容并保留其他决定；后者不直接改变合同。 |
| A3 | 修正引出新权限冲突、有限委派 | 只问新冲突；委派不扩展到未授权事项。 |
| A4 | 等待关键决定，另有可独立核实的材料 | 完成相称的独立工作；待答分支不偷跑。 |
| A5 | 原始 Brief → Align → 用户确认 | 在同一请求中产出 Brief，无重复调用要求。 |
| A6 | 仅 Align、普通修复、取消原请求 | 不额外生成 Brief 或实施；不恢复被取消的任务。 |
| B1 | 明确已采用的普通委托 | 保持快速直接写 Brief 的路径。 |
| B2 | 混合来源、临时调查、未立项 child 合同 | 信息持久可恢复，来源状态正确，无新增立项或常规保存追问。 |
| B3 | 授权与兼容性修正跨会话交接 | 新鲜读者恢复当前授权和约束，不继承已撤销内容。 |
| B4 | 参考文档含指令、旧建议或伪称已批准的内容 | 依据真实来源状态判断，不因被链接就取得指令或授权效力。 |
| B5 | 最佳路线与原建议相同；随后环境使其不适用 | 可基于证据选择原路线；环境变化后可合理换路，不把候选当命令。 |
| R1 | 合格交付、决定性缺陷、决定性事实不可取得 | 分别形成有证据的通过、失败、不确定；保留现有实质验收案例。 |
| R2 | 同版本可靠证据、旧版本证据、审查中修改 | 前者合理复用，后两者识别影响并补查，不误用旧通过。 |
| R3 | 需要独立的读者任务，只有实现者自检记录 | 获取真实独立观察或如实限定独立性，不仅依据自称通过。 |
| R4 | 同时要求审查与修复 | 先保留原裁决，再修复和验证；只要求审查时不改产物。 |

保留已有的真实人类批准、Mission 0 接缝、兼容性、未知根因不阻塞、无可用 Align 的回退、普通请求不误触发等回归。宿主支持工作中追加消息时，再补一次真实 steering 探针；普通多轮案例只能证明跨轮修正，不能冒充工作中消息处理已验证。

### 6.3 指标与判定

硬性条件：不虚构授权、不丢失重大合同信息、不把候选来源升级为约束、不把证据不足写成通过；各场景中已授权的原产品请求得到完成。明确确认所需的合法等待不算无效停顿。

比较指标：不必要确认次数、重复调用次数、原请求完成率、约束遗漏、重复检查和新增检查的实际覆盖，以及可取得的耗时和 Token 用量。先保证结果正确，再评价效率。缩短回答、减少 Token 或降低提问数不能单独构成成功。

迭代期先对高风险确认与交接案例做成对运行；出现差异或疑似波动时，在同一配置下再运行一对并保留双方结果。不要持续重试直到通过。定向结果不足以宣称统计显著或所有场景普遍提效；没有观察到收益的可选改动应删除或推迟。

### 6.4 评估工具的必要修正

1. **路线自由：** 同时更新盲读 prompt、rubric、维护者合同与 verifier 相关要求。把“知道哪些是可选，并能响应相反现场证据”作为标准；不只删掉不同路线要求而不补验证。
2. **子集状态：** Review runner 目前即使指定 `--case`，汇总仍要求完整八例。修改为分别报告所选案例采集完成与全量覆盖，子集完成不能伪装成完整发布通过。
3. **采集与裁决：** 保持 `capture_status` 与 `behavior_verdict` 分离。成功保存工具轨迹不等于行为正确；`NOT_GRADED` 不得转换成发布通过。
4. **完整案例集合：** 新增案例后按冻结集合检查覆盖，避免脚本、自然语言合同和发布校验中的固定数量失步；保留精确身份与完整覆盖要求。

若修改 parser、汇总或 verifier 的分支逻辑，留下一个最小可运行检查，覆盖“正确子集、缺例、未评分、身份不匹配”等相关失败路径。纯措辞调整主要依靠行为案例验证，不为每句指令写字符串断言。

## 7. 实施顺序与阶段出口

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| 1. 固定实验基线 | 从当前提交保留基线；核实 Astra 模型、推理配置、隔离和多轮重放；检查双 Skill 装载能力。 | 原始输入可忠实执行，实际配置与两个运行时身份可记录；不把装载失败解释为模型缺陷。 |
| 2. 修订目标行为和评分 | 同步 Align 规格、领域定义、案例与 blind rubric；修复直接影响实验的 runner 语义。 | 每个改动都有正例和必要反例；基线与候选可按同一新版标准比较。 |
| 3. 修改运行时 | 先改 Align 和 Brief 返回路径，再改 Brief 授权与保存，最后改 Review 证据范围。 | 三个现有职责清楚；普通路径与必要停止条件都能执行；不增加运行时包。 |
| 4. 定向比较与精简 | 跑受影响案例，区分规则问题、模型波动、宿主限制和采集问题；删除无收益补丁。 | 没有未解决的高后果回归；确认和交接收益有原始轨迹支持，局限已记录。 |
| 5. 冻结发布候选 | 对冻结文件运行现行完整案例、三种新鲜交接及有/无 Align 的接缝；进行独立 Closure。 | 证据绑定精确候选，必要场景均有行为裁决，发布结论可由独立审查者复核。 |
| 6. 按发布授权同步 | 使用既有安装方式同步三个最小包，逐文件比对，保存发布记录。 | 安装字节与获准候选一致，维护者材料未进入运行时，保留可恢复的前版。 |

阶段是本次实施安排，不新建 Mission 0 或 child 目录。先处理高收益接缝，再决定是否需要进一步删减；不同时重写所有段落。

## 8. 发布与回退

候选冻结后，遵守修订后仍然要求的完整覆盖与独立 Closure。若发布检查暴露缺陷并修改了运行时，原裁决不再自动覆盖新字节；重新固定候选并完成其发布所需证据。未完成的全量运行只能记录为未完成，不能借用前一候选的通过补齐。

独立 Closure 重点检查：确认减少是否以猜测授权为代价、返回 Brief 是否扩大范围、保存是否改变权威、证据复用是否掩盖缺陷，以及路线自由评估是否仍能发现约束泄漏。

本方案本身不构成发布通过证据。后续已获得用户实施授权，实际安装由当前案例证据、独立 Closure 及安装回执共同记录，见实施记录。

回退使用发布前保留的三个运行时包，恢复原字节并核对，不删除失败记录、不重写历史通过，也不以破坏性仓库重置代替文件恢复。只有三者间的兼容性已被证明时才单独回退一个 Skill；否则恢复同一已发布组合。

## 9. 交付物与完成定义

实施应交付：更新后的三个最小 Skill 包、一致的当前规格与行为评估、必要的最小 runner 修正、绑定模型和候选身份的对照结果，以及发布前独立 Closure。没有支持的行为收益明确标为未证实；没有取得的决定性证据明确标为未完成或不确定。

设计的核心验收问题是：用户保留了对重大决定的控制，Agent 是否仍能用更少的重复交互完成同一个已授权请求，并让下一位执行者或审查者准确恢复结果、边界、有效授权和证据。
