# Mission Brief: 可依赖的结果交付审查

## Outcome

`mission-review` 作为与 `mission-brief` 配对、但独立调用的 Skill，使一个未参与实施的 Agent 能够根据已经采用的委托、最终产物和现场证据，亲自判断承诺的结果是否兑现，并形成一份简洁、可追溯的 Closure Review。

审查以用户或系统实际得到的结果为中心，而不是以原句复现、报告形式或实现路线是否符合偏好为中心。

## Success

- 面对 Mission Brief 或能够恢复同等合同的明确委托，审查 Agent 能识别实际结果、合理失败、证明义务、硬边界和适用权威，不静默重写合同。
- 审查 Agent 会接触最终产物、复核实施者证据，并完成当前环境中合理可行的验证；结构存在、测试通过或实施者自评只证明它们实际检查到的内容。
- 裁决取决于实质结果。不同措辞、必要的忠实展开和未被合同限定的实现选择不会单独造成失败；真实未兑现也不会被漂亮报告或代理指标掩盖。
- 缺少现成证据时，审查 Agent 先补做能够完成的检查。只有决定性事实仍无法可靠取得时，才保留不确定性或给出 `INCONCLUSIVE`。
- 当独立阅读、使用或判断能够实质挑战成功主张时，审查 Agent 可以把原始委托和最终产物交给未参与实施的子 Agent 直接尝试；主审仍负责复核证据、作出裁决和形成报告。
- 人类只承担合同明确要求的人类决定、授权或 Agent 无法真实提供的体验。常规验证不会因为提到“用户”“读者”或“评审者”而转交给用户。
- Closure Review 给出 `PASSED`、`FAILED` 或 `INCONCLUSIVE`，并清楚呈现实际观察、决定性证据、反证、实质缺口和剩余不确定性；没有实质缺口时不为了显得严格而制造问题。
- `mission-review` 与 `mission-brief` 在同一仓库中共同维护和分享，但分别按需加载；新增审查能力不增加 `mission-brief` 的运行时规则或注意力成本。

## Evidence Required

- 对运行时包、手动调用策略和配对仓库边界进行离线检查，证明 `mission-review` 能被独立发现和加载，同时不改变已发布的 `mission-brief`。
- 在不泄露预期答案、缺陷诊断或修复方向的新鲜上下文中，使用原始委托、最终产物和实施者主张进行代表性审查。
- 行为证据至少能挑战这些相似但不同的情形：真实兑现但表达不同、代理指标假通过、决定性合同违约、证据暂不可得、主审可自行补证、合同明确要求人工参与，以及独立子 Agent 能提供有效盲审。
- 使用维护者私有的真实报告材料，检查审查 Agent 是否会实际尝试业务阅读与证据回查，而不是接受实施者验收记录或只检查报告结构。该材料不随本仓库发布。
- 保留候选身份、原始输入、输出和取证记录，使独立审查者能够区分 Skill 缺陷、证据缺口、合理方差和评估过严。
- 发布前由独立会话完成 Closure，确认 Skill 判断的是结果兑现而不是措辞符合，并且没有把审查责任推给人类或固定审批角色。

## Boundaries

- 在当前 MissionBrief 仓库内新增独立的 `mission-review` Skill；保持现有 `mission-brief` 运行时文件、调用方式和已发布身份不变。
- Skill 只审查和报告交付结果，不实施被审任务，不在同一次审查中静默修复产物后改判通过，也不修改原 Mission 合同。
- 审查强度与结果后果、不可逆性、跨系统影响和真正主观程度相称。低风险任务不承担仪式化重审，高风险任务也不以方便的代理检查代替结果证据。
- 独立子 Agent 是按需取证手段，不是每次必经的审批层；向它提供原始任务和产物，不提供主审的预期裁决。
- 维护者案例、评估记录和 Closure 不进入运行时 Skill 包。
- 行为测试中的模型调用、通用 Harness 或 Judge 建设，以及向全机 Agent 环境安装，分别需要明确授权。

## Non-goals

- 不把 `mission-review` 合并进 `mission-brief`，也不为目录对称重排现有稳定 Skill。
- 不建立逐句映射、固定问题轮数、复杂内部状态机、评分系统或案例专用禁语清单。
- 不强制执行原合同未规定的架构、工具、代码风格、报告格式或工作流程偏好。
- 不默认要求人工签核，也不把独立子 Agent 的一致意见当作无需核验的真相。
- 首版不复刻 `SkillEvalTestPlatform` 的完整自动评估设施或多次采样发布门。
